# Profiles: one assistant, any company

A profile is a directory. Swapping it swaps the company, its systems, its people, its rules
and its language; the binaries stay the same. Two profiles ship:

| | `acme` | `devteam` |
|---|---|---|
| Company | Acme GmbH (German) | Northwind Labs (English) |
| Systems | HR, CRM, IT helpdesk, documents, Jira, team chat | GitHub, team chat, incident queue, engineering docs |
| People | 7 (HR, sales, IT, finance) | 6 (developers, maintainer, SRE, PM, security) |
| Typical rules | salaries only own unit, tenants, deals ≥ 50k need approval, exports four-eyes | own repos only, merges need a maintainer, infra merges four-eyes, posts only to own channels |

## Layout

```text
profiles/<name>/
├── profile.yaml        name, locale, agents (client ids, prompts, A2A skills), messages,
│                       memory settings, admin and cost roles, suggested questions
├── models.yaml         model per agent role (provider/model), fallback
├── pricing.yaml        price per model route, budgets (per run, per user per day, per team)
├── approvals.yaml      Warden rule → approvers (role:… / user:…), four_eyes
├── docs_acl.yaml       team → document id patterns (becomes the doc_scope claim)
├── connectors/*.yaml   systems and their tools with scopes, sensitivity, tags
├── prompts/*.md        agent preambles (no permission logic in prompts)
├── warden/
│   ├── policy.yaml     roles → scopes, agent ceilings and delegation, restrict-only rules
│   ├── catalog.extra.yaml   non-MCP actions: x-memory, x-docs-page, a2a_skill
│   └── catalog.yaml    GENERATED from connectors + extra
├── scenarios/
│   ├── demo/*.yaml     scripted conversations: replay tests and the offline model
│   └── security/*.yaml Warden eval suite
├── seed/               seed.yaml (users, record counts, fixed records) + docs/*.md
├── eval/               quality-eval questions (acme)
└── data/               GENERATED by the seed: users, records, PDFs, page images, corpus, realm
```

## Connector presets

A connector is one file in `connectors/`. It names a server and lists that server's tools with
the scopes Warden checks, their sensitivity (`read` or `write`) and tags rules can match. The
server comes in three forms:

| `server:` | What runs | Use |
|---|---|---|
| `{ builtin: crm }` | one of the seven presets in `steward-mcp`, serving the profile's seed data | demos, tests, CI |
| `{ url: https://… }` | any Streamable HTTP MCP server | a real SaaS or in-house server |
| `{ command: [npx, -y, …] }` | a local stdio MCP server the gateway starts (`pass_env` lists the variables it may see) | local tools |

The presets:

| Preset | Tools | Used by |
|---|---|---|
| `hr` | search and read employees (incl. vacation days), absences, salaries (rule: own unit only) | acme |
| `crm` | deals per tenant, update, export, read-only SQL | acme |
| `ticket` | tickets and incidents: list, read, create, comment, close | acme, devteam |
| `docs` | list documents, search with verified citations; page images; via docrag-bench when configured | acme, devteam |
| `jira` | issues per project: list, create | acme |
| `chat` | list channels, post a message | acme, devteam |
| `github` | issues and pull requests per repository: list, create, merge | devteam |

Swapping a preset for the real system changes only `server:`; the tool list, scopes, policy
and approvals stay as they are. `steward profile generate` checks the files (unknown preset,
unscoped tool, duplicate names fail) and writes `warden/catalog.yaml`; `steward profile deploy`
also writes the gateway's upstreams. The console's Connectors page shows each upstream's
health; when one fails repeatedly its circuit opens and its tools disappear from every
session until it recovers (`crates/steward/tests/console.rs`).

## Making your own

1. Copy a profile: `cp -r profiles/devteam profiles/mycorp`.
2. Describe your systems in `connectors/`. A connector points at a built-in server, any
   Streamable HTTP MCP server (`server: { url: … }`) or a local stdio server
   (`server: { command: [...] }`). Give every tool scopes; unscoped tools are denied.
3. Write `warden/policy.yaml`: roles grant scopes, each agent has a ceiling, rules only
   restrict. See Warden's [policy reference](https://github.com/byQuexo/warden/blob/main/docs/policy-reference.md).
4. Route approvals in `approvals.yaml`.
5. Edit `seed/seed.yaml` and `seed/docs/`, then:

   ```bash
   cd seed && uv run steward-seed --profile ../profiles/mycorp
   cargo run -p steward -- profile generate --profile profiles/mycorp
   cargo run -p steward -- profile deploy --profile profiles/mycorp --out deploy/mycorp
   ```

6. Write demo scenarios and a security suite, then prove the profile:

   ```bash
   cargo run -p steward -- replay --profile profiles/mycorp
   warden eval --policy warden/policy.yaml --catalog warden/catalog.yaml \
     --suite scenarios/security/mycorp.yaml --generate --mutate --coverage --gate
   ```

7. Run it: `cargo run -p steward -- demo --profile profiles/mycorp` or
   `make demo PROFILE=mycorp`.

## Scenario format

```yaml
id: 03-sven-big-deal
title: "Sven ändert einen großen Deal, Sara gibt frei"
user: sven                       # who chats (impersonated_by: ines for test-as)
kill_switch: writes              # optional precondition
usage: { input_tokens: 60000, output_tokens: 1500 }   # optional, per scripted model call
turns:
  - user: "Setz den Deal d-1007 auf 80.000 Euro"
    script:                      # what the scripted model does
      - tool: { name: crm.update_deal, args: { tenant: dach, deal_id: d-1007, amount: 80000 } }
      - say: "Erledigt …"
    expect:                      # what Warden, the inbox and the assistant must produce
      - decision: { tool: crm.update_deal, effect: require_approval, rule: big-deals-need-approval }
      - approval: { approver: sara, decide: approve }
      - tool_result: { tool: crm.update_deal, contains: "80000" }
```

Script steps: `tool`, `delegate` (with the sub-agent's own `script`), `remember`, `say`.
Expectations: `decision`, `approval` (`second_approver` for four-eyes), `tool_result`,
`answer_contains`, `answer_omits`, `citation`, `abstained`, `handoff`, `memory_used`,
`memory_stored`, `memory_refused`, `budget_exceeded`, `not_executed`.
